# InfraNexus 问题处理与前端交互改造实施方案

日期：2026-10-22。本文为原 M0–M6 阶段设计，实施与验证历史保留在 [TODOLIST](TODOLIST.md) 的历史看板。M0–M6 后的新一轮工作以 [深度复审整改方案](DEEP_REVIEW_REMEDIATION_PLAN.md) 及 TODOLIST 顶部当前看板为准；冲突处以新方案为目标契约。

本文是对 [原架构方案](ARCHITECTURE_AND_PLAN.md) 的增量修订；与旧方案冲突时，本轮整改契约优先。本文制定实施方案，不表示功能已经修复，也不授权自动部署、自动提交或代替人工确认生产数据迁移。

## 1. 目标、证据与范围

目标是先封堵授权与信息泄露风险，再完成并发一致性和失败状态处理，最后增强高频管理交互。保留 Go/Fiber/GORM/Casbin、React/Base UI/Tailwind/TanStack Table 的现有技术栈，不进行无关重构或 UI 全量重设计。

### 1.1 审查基线

上一轮审查在隔离临时数据库中复现了以下行为：

| 编号 | 行为 | 对应工作包 |
| --- | --- | --- |
| F01 | 只有通用用户更新 API 权限的账号，可以提交 `role_ids` 将自身升级为 admin | S01 |
| F02 | 新实例接受公开固定管理员密码登录，初始化日志包含该密码 | S02 |
| F03 | 用户停用时旧 JWT 被拒绝，重新启用后旧 JWT 恢复访问 | S03 |

| F05 | 实际 401 响应具有 request_id，访问日志却记录 status=200、request_id 为空 | S07 |

源码还确认了 SSE 全局广播且没有连接期重新鉴权、部门校验与写事务分离、角色关联与策略提交分离、授权弹窗失败后仍可保存、乐观更新整页回滚、角色列表截断到前 100 条等问题。并发交错、跨实例策略传播和浏览器交互需要在实施中补充专门验证，不能将源码推断记为已复现。

审查时 `go test ./...`、`go test -count=1 -race ./...`、`go vet ./...`、前端 16 项测试和生产构建通过；数据库验证主要是 SQLite。此记录是历史基线，不能替代修改后的回归。

### 1.3 必须保持的工程约束

- Handler 只调用领域 Service；Service 通过领域 Repository/事务接口工作，不直接持有 GORM 事务或 Redis 客户端。
- UUID 继续使用仓库约定的 `github.com/google/uuid`，复杂新增数据使用 `datatypes.JSONType[T]`；不因本轮整改替换 UUID 库或升级依赖大版本。
- Web 保持 Cookie 会话，不引入浏览器 JWT 存储与刷新队列。外部 JWT 端点、Cookie 来源校验和统一响应继续保留。
- 业务增强放入公共业务组件、hooks、页面与全局样式，不能为业务需求直接改写 `frontend/src/components/ui/` 的生成组件。
- 保持固定视口外壳、main 单独滚动、全宽画布、12 列网格和语义颜色。动效服从减少动态效果偏好。
- 未执行的检查保持未完成；每个工作包的完成证据包括变更、命令、结果和限制。

## 2. 分期、依赖与交付门槛

优先级表示实施顺序：P0 为安全封堵，P1 为一致性与核心体验，P2 为效率增强，P3 为按性能证据启用的能力。它与漏洞严重级别不是同一概念。

| 阶段 | 工作包 | 依赖 | 交付门槛 |
| --- | --- | --- | --- |
| M0 安全封堵 | S01、S02、S04 的权限过滤、U01/U03 的安全保存 | 可分别实施 | 提权回归拒绝、无默认生产凭据、普通账号收不到目录事件、加载失败不可保存授权 |
| M1 认证与数据正确性 | S03、S07、D01、D02、D03、U04 | S01；结构变更遵循 V01 | 旧凭据不复活、清空语义准确、无半成功写入、日志状态准确、列表不截断 |
| M2 并发与授权一致性 | S05、S06、S08、S04 的连接撤销与跨实例恢复 | V01、S01、S03 | SQLite/PG 并发不成环；撤权后所有实例的新请求均拒绝 |
| M3 可靠前端基础 | U01、U02、U03、U09 | M0；U04 可并入 M1 | 网络/403/空数据可区分；未保存不丢失；键盘与焦点行为成立 |
| M4 高频效率 | U05、U06、U08 | U02/U09；树拖拽依赖 S05 | 批量选择范围准确、表格操作可达、拖拽冲突可恢复、命令无越权 |
| M5 目录任务闭环 | U07、S04 的可靠事件、任务相关迁移 | S04/S05/S06、U01/U02 | 计划变化需重审；进度可恢复；敏感明细有授权边界 |
| M6 发布验收 | V02、V03、V04 | 对应工作包 | 回归矩阵、真实双实例/PG证据、升级演练与已知限制完整 |

建议按工作包形成可独立评审的小批次变更。M0 可先发布安全封堵；高级交互和目录任务可通过能力开关逐步启用。排期前先估算事务、迁移与双实例验证成本，不以固定日历日期替代完成门槛。

## 3. 后端与数据问题处理方案

### S01：字段授权与角色授予边界（P0）

**现有入口**：`backend/internal/domain/user.go`、`handler/user_handler.go`、`service/user_service.go`、`service/role_service.go`、`service/authz_service.go`、`bootstrap/routes.go`、`bootstrap/seed_permissions.go`，以及前端用户表单与服务类型。

1. 通用 `PUT /users/:id` 仅修改昵称、邮箱、头像；移除状态、角色和部门写入。对旧敏感字段明确返回 400，而不是静默忽略后返回成功；只对这些写入 DTO 建立严格字段白名单，避免全局解码行为突变。
2. 启停、角色分配继续走现有独立端点。新增 `PUT /users/:id/department`，正文必须显式包含 `department_id`，允许 UUID 或 null，受 `users:move` 对应 API 权限保护。
3. 创建用户若带非空初始角色，除创建权限外还需角色分配能力；若带初始部门还需调岗能力。前端无对应能力时隐藏相关编辑控件，不以隐藏代替后端鉴权。
4. 后端组合授权按精确 API 对象/方法和当前 Principal 判断，不能仅凭前端按钮编码或某个祖先菜单编码推断。组合条件必须全部成立；当前前端 `hasPermission` 对数组是任一满足，不可直接用来表达 AND 条件。
5. 本方案默认采用保守授予策略：admin 角色只能由超级管理员授予；非超级管理员只能授予其自身拥有的有效 API 权限范围。分配角色、修改角色权限、修改已绑定 API 权限的 Path/Method 都需检查最终权限，避免从其他入口扩大授权。
6. 菜单可由后代权限推导，但菜单存在不代表获得全部后代 API。目标角色/权限 ID 去重并完整校验，不存在的 ID 返回错误，不能静默丢弃。

**验收**：仅 `users:update` 对应 API 授权的用户不能更新 role_ids/status/department_id；不能自升 admin；直接调用接口与前端入口结果一致。对创建附带角色、角色授权和权限 Path 变更分别编写越权回归。

### S02：管理员初始化与生产密钥（P0）

**涉及**：`backend/internal/bootstrap/seed.go`、`internal/config/config.go`、`bootstrap/app.go`、`cmd/server/main.go`、`backend/config.yaml`、README 与种子测试。

- 种子数据与管理员凭据初始化分离。首次初始化必须显式提供一次性 bootstrap 密码；已有管理员时不因重启重置密码。
- 推荐增加独立初始化命令。正常服务启动不输出口令、不暗中创建固定口令账号；开发环境使用显式启用的演示初始化，测试独立注入凭据。
- 生产启动拒绝空值、仓库默认 JWT 密钥和过短密钥；保持现有目录加密密钥检查，文档区分两种密钥用途与轮换影响。
- 既有安装中检查是否仍使用已公开默认密码；拒绝以“种子已改”代替既有账号整改。升级说明给出显式改密及凭据撤销步骤，不静默锁死所有管理员。

**验收**：首次启动缺配置给出可操作错误；无固定默认口令；重启不改用户密码；日志不含口令/Token/绑定密码；既有数据库升级流程可演练。

### S03：停用、改密与认证版本（P1）

**涉及**：`domain/user.go`、`domain/auth.go`、`service/auth_service.go`、`service/user_service.go`、`repository/auth_repository.go`、用户持久化与迁移。

- 增加 `users.auth_version`，存量回填为 1；Session 与 Access/Refresh Claims 记录签发版本。
- 停用、重置密码及明确的安全撤销操作，原子递增版本；启用不能降低版本。LDAP 停用用户也走同一领域规则，不能直接更新 status 绕过撤销。
- Session、Bearer 和 Refresh 均比较当前用户版本；缺版本或版本不匹配拒绝。角色变化仍实时读取，策略变更由 S06 处理。
- 版本原子递增放在 Repository 中；不使用先读再写的 `version+1` 来实现并发撤销。
- 版本上线会使旧格式凭据失效，采用一次受控重新登录窗口；部署期间禁止新旧认证服务混跑。数据库字段保留可前向兼容，但不能回滚到接受无版本凭据的旧认证逻辑。
- 状态撤销后的“撤销操作”仅表示重新启用账号，不能恢复已撤销会话；前端明确提示需要重新登录。

**验收**：Cookie、Access、Refresh 在停用→启用后均不复活；同秒改密、并发撤销、LDAP 停用均覆盖；新登录签发当前版本。

### S04：SSE 授权、生命周期与恢复（P0 封堵，P1/P2 完整化）

**涉及**：`handler/sse_handler.go`、`domain` 事件/订阅接口、认证与授权 Service、Fiber 装配、`frontend/src/stores/notifications.tsx`、`stores/auth-context.tsx`、`services/api.ts`、`layouts/header.tsx`。

1. 将全局 Hub 移到独立基础设施实现并通过领域事件接口注入，Handler 只调订阅 Service，禁止 Service 反向依赖 Handler。
2. 订阅绑定 user_id、Session/Family ID、auth_version 和取消句柄；明确只支持带 Cookie 的浏览器 EventSource，外部 Bearer 客户端使用支持请求头的流客户端，不把 Token 放入 URL。
3. M0 先按订阅者权限过滤目录事件。完整阶段在事件投递前校验当前身份与读取目录日志所需 API 权限；会话/授权状态不可确认时停止敏感投递，不使用无限期缓存权限。
4. 公开通知载荷仅含事件 ID、任务 ID、阶段、计数和脱敏错误码。用户名/DN/原始错误只在受控日志详情接口中返回。普通通知与目录任务使用明确事件类别及授权要求。
5. 注销、认证版本变更或会话失效时关闭订阅；撤销消息丢失仍由投递检查和周期验证兜底。周期检查不能给空闲 Session 续期，心跳不视为用户活动。
6. SSE 采用可排序事件序号、有限持久化保留和队列上限；Last-Event-ID 只恢复当前身份有权访问的事件。队列溢出/超过保留窗口告知客户端重新取任务快照，不能悄悄丢完成事件。
7. 多实例通过共享事件存储/消息通知分发，进程内 Hub 只管理本地连接。Redis 通知可作为唤醒信号，任务数据库快照是恢复依据。
8. 前端统一处理手动退出、401、账号切换：取消可取消查询、清理敏感缓存、清空通知并关闭连接；忽略上一身份的迟到响应与事件。请求携带 AbortSignal，使用认证 generation 防止不可取消响应污染新账号。
9. 无鉴权权限的终止状态停止反复重连；短暂网络中断退避重试。EventSource 无法读取错误响应时，用受控身份探测区分会话失效和网络中断，不能仅凭 onerror 宣称退出。

**验收**：普通账号收到零目录敏感事件；注销后旧连接不再收到任务事件；A 退出后 B 看不到 A 的缓存/通知；权限撤销与跨实例重连均有集成测试。

### S05：部门结构与批量调岗事务（P1）

**涉及**：部门/用户/LDAP Service 与 Repository、`domain/department.go`、领域 UnitOfWork 接口及数据库迁移。

- 新增单行 `organization_state`（UUID 主键、revision）。所有结构写入先在事务内原子更新该行以取得写入互斥，再读取和校验。SQLite/PG 的具体事务与忙等待策略由仓储封装。
- 部门创建/移动/删除/排序、父路径相关更新、LDAP 建部门、人员调岗和用户创建带部门关联，都遵循同一锁协议；只给 Move 加进程内 mutex 不合格。
- 事务内校验自引用、后代循环、最深层级、同级唯一、父部门存在/状态、成员/子部门删除保护，再更新节点和全部后代路径。
- 部门普通资料编辑避免整实体 Save 把并发更新后的 parent_id/tree_path 覆盖；结构字段只能通过结构事务修改。
- 树读取返回 `tree_revision`；交互性变更携带 `expected_revision`。版本不匹配返回 409 和稳定冲突业务码，不泄露数据库错误。
- 批量调岗在同一事务校验目标、去重并确认全部用户有效、完成更新和核对影响行数；任何不符合预期均回滚。PG 用户行按 UUID 稳定顺序锁定。
- 冲突/忙等待采用有界重试；涉及预期版本的业务冲突返回用户重新确认，不自动替用户移动到变化后的目标。

**验收**：屏障控制的 A→B 与 B→A 并发操作不能同时成功；删除/新建/调岗/LDAP 交错后 parent_id 与 tree_path 一致、无孤儿；任意批量成员失效不产生部分成功。

### S06：授权持久化与多实例策略一致性（P1）

**涉及**：`service/authz_service.go`、`service/role_service.go`、`service/permission_service.go`、相关仓储、`bootstrap/casbin.go`、Casbin 中间件和迁移。

- 定义业务角色关联为授权事实来源。角色/权限关联、派生 `casbin_rule`、授权 revision 和 Outbox 事件在同一数据库事务提交；Casbin 持久化适配器的具体写法放 Repository。
- 不在业务事务未提交时调用带自动保存副作用的 Enforcer 方法。先生成完整目标策略再事务写入；失败必须回滚，不能只写完关联再尝试内存同步。
- 增加全局授权 revision。请求进入 Enforce 前核对数据库已提交 revision；本地落后时在锁保护下加载稳定版本，失败返回 503，不能继续沿用旧允许策略。
- 加载前后比较 revision，发生并发变化则有限重试；不能把读取中的混合策略标记为最新。版本切换和 Enforce 的并发互斥需封装，不仅保护单个写 API。
- Outbox 消费者可重试、幂等，发布跨实例刷新信号；启动和重连执行补偿。Watcher/Redis 广播优化刷新速度，不作为撤权正确性的唯一保证。
- 基线先接受每个受控请求一次轻量 revision 查询；若优化为缓存，必须另立明确的撤权延迟契约和验证，不能悄悄降低一致性。

**验收**：关联写/策略写失败时全部回滚；双实例中 A 撤权提交后，B 新进入鉴权的请求拒绝；通知丢失、重启、加载失败仍安全；已进入处理中的请求不承诺追溯取消。

### S07：错误映射、日志与被忽略错误（P1）

**涉及**：`middleware/request_log.go`、`core/errors/errors.go`、`core/response/response.go`、`bootstrap/database.go`、认证/用户/LDAP Service 与 Handler。

- request_id 统一使用 `requestid.FromContext`；响应、访问日志、错误日志、异步任务关联保持一致。
- 提取无写响应副作用的错误分类器（HTTP/业务码/安全提示），供日志和 ErrorHandler 复用。避免中间件为拿状态而执行两次 ErrorHandler。
- 访问日志区分实际错误状态并记录内部原因；服务层不重复记录同一个错误。GORM slog 适配器从 Context 提取 request_id，禁用敏感 SQL 参数输出。
- 异步任务记录 task_id、operator_id、触发请求关联 ID，不能持有 Fiber Ctx 到后台 goroutine。
- 逐项分类 `_ =`：认证存储与偏好会话更新失败不能静默成功；非关键 last_login_at 失败可不阻断登录，但应有脱敏日志。清理失败必须有可重试或可观测处理。

**验收**：400/401/403/404/409/500/503 的日志与响应一致；request_id 非空且对应；敏感字段不出现在日志中；偏好更新部分失败不谎称已全部生效。

### S08：路由同步与权限防漂移（P1）

### U07：LDAP 任务向导、Diff 与进度（P2）

**涉及**：LDAP page/config-sheet/preview-dialog/sync-status、LDAP Service/Repository/DTO、通知与 Header。**新增**：任务详情、字段 Diff、步骤展示业务组件。

流程为“检查配置 → 生成预览 → 确认影响 → 执行 → 查看结果”。现有快捷“立即同步”在计划校验完成后也走相同确认契约，不保留绕过高风险停用确认的旁路。

**计划与执行契约**：

- Preview 返回 plan_id、生成时间、有效期、配置版本、相关本地记录版本、目录数据指纹、摘要及分页明细。默认计划有效期 10 分钟，可配置；绑定操作者并重新检查执行权限。
- Diff 明确字段 before/after；敏感口令永不返回，DN/邮箱受目录读取权限保护。计划存储设置短 TTL 和清理任务，不能永久堆积目录个人信息。
- Sync 接受 plan_id、幂等请求 ID；执行前重新读取目录与相关本地版本，变化返回 409 要求重新预览。幂等记录按操作者+配置+请求 ID 保存，重试返回同一任务。
- LDAP 没有一致性快照保证时，界面明确“根据预览数据执行；后续目录变化将在下一次同步处理”。校验通过后使用已批准计划，不声称能锁住外部目录。逐用户更新使用预期版本，期间冲突标为失败且不覆盖新资料；整体允许部分失败并准确报告。
- 全量停用数量较大时显示受影响账号清单与增强确认；预览条目被分页/截断必须注明，统计基于完整计划，不以可见明细数代替全部影响。

**任务与事件契约**：

- 新增受控 `GET /ldap/sync-logs/:id` 获取任务快照/报告；新权限挂在目录读取能力下。M0 已建立的读取权限不可被“知道任务 UUID”替代。
- 保留开始/完成事件，增加 progress，数据含 event_id、task_id、phase、processed、total、各动作计数、时间和脱敏错误码。兼容阶段通过 schema_version 或明确版本化事件处理旧客户端。
- phase 为 preparing/planning/applying/finalizing；准备阶段 total=null，使用不确定进度；执行阶段 total 是计划操作项总数，含不变/跳过/缺失停用项，不能直接用目录用户总数作为分母。
- 任务快照周期持久化，进度推送节流至每任务每秒不超过 2 次，终态强制持久化并发布。服务重启、任务失联和原有超时锁回收规则要协调；增加 owner/lease 心跳，旧 worker 不得在失去租约后继续写入。
- SSE 只触发进度/快照刷新，日志数据库是最终事实；重连或刷新先取快照。失败报告可按原因筛选；“重试失败项”需重新计划校验，不直接重放旧写入。

**验收**：计划过期/配置变化/本地记录变化均需重审；重复点击只创建一个任务；刷新/断线恢复计数；进度不倒退且不超过 100%；未授权账号不能读取快照和 Diff。

| --- | --- | --- |
| users.auth_version；Session/JWT 对应字段 | 安全撤销 | 用户回填 1，旧凭据一次受控失效 |
| users/roles 的 edit_revision | 行内编辑、授权草稿冲突检查 | 回填基线，写入原子 CAS；与 auth_version 含义分离 |
| organization_state | 树事务锁与结构 revision | 单行 UUID 主键，所有相关写入口接入后才启用拖拽 |
| authorization_state + policy_outbox | 策略版本与可重试广播 | 业务关联、派生策略、revision、事件同事务 |
| 同步计划、任务快照/lease、事件序号 | Diff、进度与恢复 | 计划/事件有限保留，终态日志按既定保留策略 |
| 迁移版本记录 | 有序迁移与升级诊断 | 版本化、可重复检测；不能仅依赖 AutoMigrate |

- 新领域表使用 UUID；单例状态表也遵守 UUID 主键约定。Outbox/计划载荷用明确结构的 JSONType，schema_version 与事件 ID 独立。
- 增加部门单用户端点、任务详情端点及对应种子权限；同步前后检查权限树与 API 矩阵，不能仅改前端。
- `department/tree` 响应若从数组扩为带 revision 的对象，必须显式升级客户端与类型；迁移期可用响应头暴露 revision，最终选一种并记录，不让同 URL 随机返回两种形状。
- 新业务错误分配 HHHCCC 常量，如版本冲突/计划过期对应 409、授权存储不可用对应 503；数值实施前在统一清单登记，禁止复用不相干语义。
- 升级顺序：备份并验证 → 加字段/回填 → 部署安全后端及匹配前端 → 更新权限种子/重建策略 → 失效旧凭据 → 冒烟 → 开交互开关。认证版本阶段不进行不兼容滚动混跑。
- 回滚优先关闭交互开关与前向修复；不回退到允许提权或旧会话复活的版本。已提交数据不得靠删除数据库/自动降级来回滚。

## 6. 验证矩阵与交付标准

### V02：后端与集成

| 场景 | 必须证明 |
| --- | --- |
| 字段/角色越权 | 更新、创建附带角色、角色授权、API Path 改写均不能扩大无权授予的能力 |
| 初始化与撤销 | 无固定口令；旧格式失效可解释；Cookie/Access/Refresh 不复活 |
| 树并发 | 双向移动、删除与调岗、LDAP 建部门交错，结构与计数一致 |
| 策略事务 | 数据库任意阶段故障不产生半提交；双实例通知丢失不保留旧允许策略 |
| SSE | 事件过滤、会话到期、注销、权限撤销、缓冲溢出、跨实例重连和快照恢复 |
| LDAP | 过期计划、版本冲突、幂等、租约丢失、部分失败与进度分母正确 |
| 响应/日志 | HTTP/业务码/request_id 对齐；敏感内容不泄漏 |
| 数据库 | 真实 SQLite 与 PostgreSQL 同契约测试；PG 不可用时明确标记未完成 |

并发测试优先使用屏障、注入时钟和故障桩，不依靠长 sleep 撞概率；`-race` 通过不等于数据库事务交错已通过。Redis 可用测试服务验证原子行为，跨进程用共享数据库与真实消息/存储实现验证。

### V03：前端与浏览器

- 增加必要的组件/交互测试能力；现有 Vitest 主要测试纯函数，不能代替表单与浏览器验收。新增测试依赖单独评估，锁文件同步。
- 自动化覆盖查询失败、安全保存、dirty guard、回滚隔离、Shift 范围、授权搜索范围、命令取消、身份切换、任务恢复。
- 浏览器验证登录→受限账号→管理页、表单返回/遮罩/Esc、拖拽与键盘替代、移动横向表格、SSE 重连。网络面板检查无多余未授权请求。
- 视口至少 320/768/1440/2560px；亮暗主题、减少动态效果；axe 类检查与手工键盘/读屏抽查结合，不能把自动扫描当作完整无障碍通过。

### V04：性能、发布与验收记录

- 在记录硬件/浏览器的固定环境采样：普通列表最大页、500 条预览、1,000/10,000 节点测试树；大规模树允许作为压力样本，不承诺业务必须全量渲染。
- 记录输入响应、提交时间、渲染节点数、长任务、接口延迟与 bundle 变化。候选目标：本地过滤输入 p95 <100ms、无明显 >50ms 连续主线程任务；以基线评审后固化为门槛，不将目标记为实测结果。
- 授权 revision 每请求查询、SSE 投递校验与任务持久化的额外负载分别采样；不得为性能绕过安全检查。
- 每工作包完成需：关联任务 ID、变更文件、行为说明、运行命令/结果、浏览器证据（适用）、未覆盖项、迁移/兼容影响。文档更改与代码更改同批维护。
- 常规命令：`cd backend && go test ./...`、`go test -race ./...`、`go vet ./...`；根目录执行 `npm --prefix frontend test`、`npm --prefix frontend run build`；E2E 命令在工具接入后记入项目 scripts，不能记录不存在的命令为通过。

## 7. 不纳入首批交付的范围

- 全站重设计、技术栈大版本升级、引入重复 UI/状态库、多租户、离线 PWA 推送。
- 任意字段的通用行内编辑、默认跨页全量选择、为所有分页表强制虚拟化。
- 自动删除失效权限、静默覆盖授权冲突、自动执行生产迁移或部署。

上述项目可以后续另立任务；它们不阻塞 M0 安全封堵和 M1 数据正确性修复。
